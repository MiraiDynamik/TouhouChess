# 分阶段棋子估值实验（Windows）

第一阶段只测妖精，普通兵作为对照。确认结果和方法后，第二阶段再测恋：分别做恋对兵、恋对妖精的直接交换实验。当前命令不会启动恋的实验，也不会改游戏估值、部署价格或难度参数。

## 安装与运行

在仓库根目录、Miniconda Prompt 或已经初始化 conda 的 PowerShell 中执行：

```powershell
conda activate TouhouChess
npm ci
python lab/piece_value.py --workers 12 --out lab/out/fairy-pilot
```

需要项目已有的 Node.js 和同名 Conda 环境；Python 工具仅用标准库，不需要额外 pip 安装。引擎使用 `engine/` 的同一实现，通过 `cli/value-match.mjs` 调用；Python 负责实验编排和统计。

默认每手 3 秒，12 个 worker，每个条件 2 对换色。共 **60 局**：普通兵对照、妖精先验估值 1、妖精先验估值 2，分别测试每枚对应 0、1、1.5、2、3 兵的五档交换。先跑小样本查看方向和未决比例，不会自动升级为长时间正式实验。

只生成和校验计划，不下棋：

```powershell
python lab/piece_value.py --workers 12 --out lab/out/fairy-pilot --plan
```

之后去掉 `--plan`，相同命令即可开始。`manifest.json` 保存每局初始阵容、种子、先验和执色。

确认试跑设计后，可在**新目录**增加样本，例如每格 20 对、共 600 局：

```powershell
python lab/piece_value.py --workers 12 --pairs 20 --out lab/out/fairy-20pairs
```

这仍不保证能得到窄区间。是否继续加样本应结合报告判断，尤其注意重复阵容和大量未决；不能只靠重复同一开局堆高可信度。

## 暂停、续跑和报告

- Ctrl+C 停止，每个完成的 ply 都保存。再次执行原命令，已结束的局跳过，未结束的局从保存状态继续。
- 可以改变 `--workers`；其他参数、引擎及实验源码、Node 版本必须一致。修改这些内容请使用新输出目录。
- 续跑不会恢复内存置换表，因此之后的着法可能与连续运行不同。
- 每个目录仅允许一个运行器。异常退出留下 `.running.lock` 时，先确认对应程序已停止，再删除锁文件。
- `--summary` 和 `--export-pgn` 也使用同一把目录锁；请停止对局后再单独执行。运行时主进程会自动更新报告，不需要另外开汇总命令。
- `games/*.json` 是进度和完整棋谱；`report.md` 是人类可读报告，`summary.csv` 是分组统计，`games.csv` 是逐局结果与阵容。不要只保存报告而丢弃 JSON。
- 每局结束同时输出 `games/*.pgn`；普通兵对照为标准 PGN，妖精组为仙灵扩展。已有 JSON 可用同一命令加 `--export-pgn` 单独转换，不必重跑。格式及导入永琳分析的方法见 [PGN 文档](PGN.md)。
- Windows 的 Excel 占用 CSV 时，程序会跳过该次 CSV 更新，不影响对局；关闭 Excel 后重新生成即可。

只重新生成报告，不继续下棋：

```powershell
python lab/piece_value.py --out lab/out/fairy-pilot --summary
```

## 实验如何测量

以香草阵容为底，实验方用两个异色兵位的妖精替换两个普通兵，再移除一方的若干兵构造交换档位。例如两妖精替换两兵、再从实验方撤一个兵，即测试“两妖精对三兵”，每枚名义交换量 1.5。阵容位置按种子选择，同一条件成对交换执色。

`--equivalents 0,2,3,4,6` 指的是**两枚合计**的对照兵数；报告会除以二。普通兵对照使用同样程序，将“被测棋子”仍设为兵：检查它是否能识别多兵、等兵、少兵的方向。

双方都由永琳控制。每组双方使用相同被测子先验估值，默认分别试 1 和 2，以检查结论是否依赖引擎预先认为妖精值多少。输入估值不是测量答案，也不按哪个估值胜率最高来定价。

默认只用 `pawn` 场景，直接对兵。可单独指定 `--contexts pawn-no-bishops` 检查无双象环境；`minor` 和 `minor-no-bishops` 则替换两马，额外依赖两马约六兵的假设，只能作为辅助场景。不同场景用不同目录，不混为同一个价值。

只接受引擎规则下的自然终局，包括将杀、逼和、重复和五十回合和棋。默认达到 400 ply 尚未结束标为未决，**不根据子力或引擎评分判胜，也不算和棋**。完整状态、历史、走法和搜索深度均保留。

## 怎样与 Ferz 比较

妖精的走法就是 Ferz：斜向一格。GNU XBoard 的 [Betza 记法](https://www.gnu.org/software/xboard/whats_new/rules/Betza.html) 将其标为 F；[Makruk 规则表](https://www.gnu.org/software/xboard/whats_new/rules/Makruk.html) 中相同走法的 Met 估值为 1.5。该数值来自另一种规则和兵种环境，只作为参照，不能要求本游戏必须测得精确的 1.5。

先看普通兵对照是否有正确方向，再看妖精在 1、1.5、2 兵各档的得分率、未决率和两种先验的一致性。1.5 档接近 50% 只说明与参考相容，不能单凭“不显著”证明等价。若要声称近似等价，还需要预先约定容差和足够精度的独立样本。

报告按完整换色配对给出保守 Hoeffding 区间，未决分别按全负、全胜扩展上下界。区间是逐格的，依赖样本近似独立；同一开局反复运行的时间噪声不是新的独立阵容。对照通过只是必要检查，不证明引擎无偏。

两枚妖精的平均交换价值包含异色配合收益；开局位置、兵的升变潜力和引擎水平也会影响结果。不要直接把测得区间作为单枚部署价格。

第二阶段等第一阶段结果出来后设计：恋对普通兵、恋对妖精直接交叉验证，并区分兵位、轻子位及后排互保场景。妖精的参照值使用第一阶段区间，不直接取当前部署价格。

## 程序自检

```powershell
python -m unittest discover -s tests -p test_piece_value.py
```

覆盖阵容合法性、换色一致性、名义补偿、未决统计、逐手保存续跑和报告生成。开发机已进行短时端到端试跑；尚未在 Windows 实机验证或完成正式价值测量。

并发回归还覆盖 12 workers 的 12 局短测试、三个写入入口的锁互斥、重复对局 ID 拒绝，以及模拟 Windows 文件占用后的替换重试。JSON/PGN 临时文件按进程 ID 区分，写入与替换分别重试；CSV/Markdown 由主线程串行更新。文件锁测试不能代替 Windows 实机验证。
